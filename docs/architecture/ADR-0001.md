# ADR-0001: Framework-First Architecture over Single-Language-First

**Status:** Accepted
**Date:** 2026-07-10
**Deciders:** Founder (Bernard Abuto), AI CTO

## Context

Sauti Labs' mission is to build reusable infrastructure for African speech
and language intelligence, not a single-language product. Before writing
any code, we had to decide how the monorepo should be organized: around
one initial language (e.g. Kiswahili-first), or around the reusable
frameworks that every language program will eventually depend on.

## Decision

We chose a **framework-first** directory structure. The repository is
organized around reusable frameworks (`frameworks/`) — annotation,
dataset management, corpus registry, benchmarking, model registry, and
APIs — with individual language programs (`languages/`) built on top of
them, rather than embedding framework logic inside a single language's
codebase.

## Directory Structure

- `frameworks/` — Reusable infrastructure shared by all language programs
  - `annotation-framework/`
  - `api-framework/`
  - `benchmark-framework/`
  - `corpus-registry/`
  - `dataset-framework/`
  - `language-program-framework/`
  - `model-registry/`
- `languages/` — Individual language programs (Kiswahili, Dholuo, Yoruba, etc.)
- `research/` — Papers, experiments, benchmarks
- `docs/` — Architecture and operational documentation
- `scripts/` — Automation and tooling
- `.github/` — CI/CD workflows and repository configuration

## Rationale

This decision is a direct application of the Master Blueprint's Six
Pillars and the Engineering Roadmap's Engineering Doctrine, which states
that no work should bypass the layered dependency chain: Languages →
Data → Models → Platform → Products. If we built a single language
first, framework logic would inevitably get tangled inside that
language's code, and every subsequent language would either duplicate
that logic or require an expensive extraction refactor later.

Framework-first means the second, tenth, and hundredth language program
all plug into the same annotation pipeline, dataset registry, and
benchmark suite from day one. This directly serves the Roadmap's Era I
milestone: "The company becomes capable of building high-quality
multilingual datasets" — capability, not a single dataset.

## Consequences

**Positive:**
- Every language program is consistent and interoperable by construction.
- New languages onboard faster once frameworks mature.
- Avoids a costly later migration from single-language to multi-language architecture.

**Negative:**
- Slower initial visible progress — no working language demo in Week 1.
- Frameworks must be designed with foresight before real language data
  stress-tests them, carrying some risk of early over-engineering. We
  mitigate this by building frameworks incrementally, validated against
  the first real language program (Kiswahili) as soon as Era I begins.

## Alternatives Considered

**Single-language-first (e.g. Kiswahili):** Rejected. Would produce
faster short-term visible results but risks hardcoding
Kiswahili-specific assumptions into what should be language-agnostic
infrastructure — directly contradicting the Blueprint's core philosophy
that "we do not build AI for African languages, we build AI with
African languages at its foundation."
